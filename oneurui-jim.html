오늘의짐.

보관함을 찾는 것보다, 짐을 다시 찾으러 가는 동선이 더 문제였습니다.

여행 중 캐리어를 잠깐 맡길 때 사람들은 가장 가까운 보관함부터 찾습니다. 그런데 방문 일정을 마친 뒤 짐을 회수하러 돌아오는 길까지 계산하면 처음 선택이 오히려 불편할 수 있습니다. 이 문제에서 출발해 보관함 위치와 이동 동선을 함께 비교하고, 보관 정보는 브라우저에서 안전하게 관리하도록 기획·구현한 팀 프로젝트입니다.

02 / PROBLEM SOLVING

만들면서 마주친 문제를
이렇게 해결했습니다.

기능을 나열하는 대신, 처음의 생각과 수정한 이유, 그 결과를 순서대로 기록했습니다.

CASE 01 PROBLEM → CHANGE → RESULT

‘제일 가까운 보관함’이 답이 아니라는 데서 시작하다

어떤 점이 문제였나

기존 검색은 현재 위치에서 보관소까지의 거리만 강조하기 쉬웠습니다. 실제로는 짐을 맡긴 뒤 목적지에 갔다가 다시 회수하고 숙소나 귀가 지점으로 이동합니다.

이렇게 바꿨습니다

출발지→보관소→방문지→보관소→최종 목적지의 4개 구간을 기준으로 동선을 계산하도록 설계했습니다. 짐을 든 이동 시간과 보관소를 경유해 발생하는 우회 시간을 별도로 고려했습니다.

결과와 의미

보관소 선택 기준을 단순 거리에서 ‘하루 전체 동선의 부담’으로 바꿨습니다.

CASE 02 PROBLEM → CHANGE → RESULT

공공데이터가 비어 있는 곳은 있는 것처럼 보이지 않도록

어떤 점이 문제였나

코레일·지자체·교통 운영기관별 보관함 자료의 형식과 지역 범위가 달랐고, 일반역·KTX·도시철도 데이터를 한 번에 확보하기 어려웠습니다.

이렇게 바꿨습니다

보관함 데이터를 출처별로 확인해 역·시설 기준으로 정리하고, 제공 범위와 누락을 구분해 다뤘습니다. 실시간 점유 센서가 없는 경우 빈자리 확정 정보처럼 표현하지 않는 방향으로 설계를 보완했습니다.

결과와 의미

공공데이터를 ‘많이 모았다’고 주장하기보다 어느 범위까지 신뢰할 수 있는지 함께 보여주는 서비스로 정리했습니다.

CASE 03 PROBLEM → CHANGE → RESULT

보관함 번호·암호를 메모장에 남기는 문제까지

어떤 점이 문제였나

여행 중 급하게 저장한 보관함 번호와 비밀번호는 사진이나 일반 메모에 남아 노출될 수 있습니다.

이렇게 바꿨습니다

서버에 비밀번호 원문을 보관하지 않고 브라우저의 Web Crypto API 기반 암호화 흐름을 적용했습니다. 표시·복사·보관 종료를 분리해 필요한 순간에만 정보를 확인하도록 구성했습니다.

결과와 의미

동선의 편의성과 보관 정보의 관리라는 두 문제를 한 서비스 흐름 안에서 다루었습니다.

03 / RESULTS & LEARNINGS

검증하고, 남긴 결과

데이터와 보안 기능은 실제 이용 상황을 기준으로 해석했습니다

프로젝트 저장소에는 역별 데이터 정리와 경로 산출 검증 기록이 있습니다. 다만 모든 보관함의 실시간 빈자리나 현장 이용 가능 여부를 확인해 주는 서비스는 아니므로, 데이터 범위와 운영기관 정보를 함께 확인해야 합니다.
