GIGANG.

개별 이벤트를 보는 것을 넘어, 왜 위험한 사건인지 설명할 수 있게 만들었습니다.

사내 자료 조회, 브라우저 AI 서비스 접근, 붙여넣기와 파일 첨부 시도가 서로 다른 로그로 남으면 위험의 전후 관계를 놓치기 쉽습니다. GIGANG은 이를 하나의 관제 흐름으로 연결한 팀 프로젝트입니다. 저는 관제 화면 UI를 제외한 주요 수집·분석·서버 및 단말 대응 기능 구현을 주도하며, 실제 이벤트를 연결하는 과정에서 발생한 문제를 해결했습니다.

02 / PROBLEM SOLVING

만들면서 마주친 문제를
이렇게 해결했습니다.

기능을 나열하는 대신, 처음의 생각과 수정한 이유, 그 결과를 순서대로 기록했습니다.

CASE 01 PROBLEM → CHANGE → RESULT

서로 다른 로그를 하나의 사건으로 이어 붙이다

어떤 점이 문제였나

브라우저 확장, 로컬 에이전트, DB 감사 로그의 이벤트 형식과 전달 경로가 달라 일부 정보가 누락되거나 같은 이벤트가 중복 처리될 수 있었습니다.

이렇게 바꿨습니다

수집된 정보를 공통 형태로 맞추고 서버·수집기·상관분석 엔진을 연결했습니다. 복사·다운로드·OCR 이벤트의 전달 형식과 누락된 수신 경로 등 연동 문제도 보완했습니다.

결과와 의미

회사 자료 관련 행동과 이후 외부 입력 시도를 같은 맥락에서 판단할 수 있는 기반을 만들었습니다.

CASE 02 PROBLEM → CHANGE → RESULT

고정 점수 대신 ‘어떤 자료였는가’를 반영하다

어떤 점이 문제였나

복사·캡처·다운로드나 외부 입력에 고정된 위험 점수를 주면 자료 민감도와 실제 연관성이 달라도 같은 위험으로 표시되는 문제가 있었습니다.

이렇게 바꿨습니다

부서별 정책, 민감정보 유형과 건수, 원본 자료 지문 일치 여부, 현재 WATCH 상태 등을 반영한 점수 계산식을 정리했습니다. 사건별 점수와 사용자 요약 점수를 분리하고 중복 가산도 막도록 보완했습니다.

결과와 의미

NORMAL·WATCH·HIGH 상태뿐 아니라 ‘왜 이 점수가 나왔는지’ 근거를 사건 단위로 남길 수 있게 했습니다.

CASE 03 PROBLEM → CHANGE → RESULT

목업 화면이 아니라 실제 수집 이벤트로 검증하다

어떤 점이 문제였나

디자인이 완성돼 있어도 고정된 예시 데이터로만 화면이 채워진다면, 실제 서버 수신·판단·대응이 이어지는지 알 수 없습니다.

이렇게 바꿨습니다

Railway와 로컬 에이전트에서 들어온 로그가 관제 화면에 반영되도록 연결하고, 화면의 사건 목록·심각도·정책 상태를 확인했습니다. HIGH 사건 Slack 알림 및 정책 제어 흐름도 구성했습니다.

결과와 의미

직접 진행한 테스트에서 이벤트 수신, 상태 분류, 케이스 반영 등 연동 결과를 확인했습니다. 화면 수치는 시험 시점의 데이터로 기록했습니다.
