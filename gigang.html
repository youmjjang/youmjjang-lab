GIGANG.

개별 보안 로그를 넘어, 자료 접근부터 외부 전송 시도까지 연결하고 대응하는 통합 보안관제 플랫폼

브라우저·Windows 단말·사내 DB의 이벤트를 수집하고 정규화한 뒤, 정책 기반 위험도 점수와 3-Hop 상관분석으로 사건 맥락을 파악하도록 만든 팀 프로젝트입니다. 관제 UI를 제외한 수집·분석·대응 기능의 주요 구현을 주도했습니다.

PythonFastAPI / RailwayChrome ExtensionWindows AgentSQLiteGeminiSlack

01 · PROBLEM

어떤 이벤트가 연결되어 있는지
보이지 않는 문제

사내 DB를 읽은 이력, 브라우저에서 외부 AI를 이용한 기록, 붙여넣기·파일 첨부 이벤트가 서로 분리되면 자료 유출 위험을 정확히 판단하기 어렵습니다. 접속 사실만으로 차단하면 정상적인 업무도 방해할 수 있습니다.

분리된 로그

DB·브라우저·단말에서 서로 다른 형식으로 발생하는 데이터를 연결하기 어려움

고정 위험도

같은 행동도 자료의 민감도·건수·일치 근거에 따라 위험이 달라지는데 동일 점수로 평가하는 한계

사후 대응 지연

외부로 자료가 이동한 뒤에만 판단하면 선제 감시와 정상 업무 구분이 어려움

02 · ARCHITECTURE

수집에서 판단과 대응까지

01 / COLLECT이벤트 수집

Chrome Extension·Windows Agent·DB 접근 기록

02 / NORMALIZE정규화·연계

Railway 수신 API·공통 이벤트 스키마·중복 억제

03 / ANALYZE위험도·상관분석

자료 연관성·민감도·건수·3-Hop·NORMAL/WATCH/HIGH

04 / RESPOND관제·대응

인시던트 관리·정책 제어·HIGH Slack 알림

Gemini는 미승인 AI/SaaS 도메인에 대한 보조 분석으로 사용하며, 정책과 사건 판단을 전부 대체하지 않도록 구성했습니다.

03 · IMPLEMENTATION

핵심 기능과 개선 내용

근거 기반 동적 점수 산정

기존 고정 점수 대신 부서 정책, 민감정보 종류·건수, 회사 자료 지문 일치 여부를 반영해 사건별 점수와 근거를 계산하도록 개선했습니다.

3-Hop 상관분석 및 상태 관리

DB 접근 → 단말 행위 → 외부 서비스 사용의 흐름을 연결하고, NORMAL·WATCH·HIGH 상태와 시간에 따른 감시 해제를 관리합니다.

실제 데이터 기반 관제

Railway와 로컬 에이전트 이벤트가 수집·정규화되어 관제 화면에 나타나도록 연결했고, 테스트 시 고정 목업 사건에 의존하지 않도록 변경했습니다.

정책 제어 및 알림

도메인 차단·일시 허용 정책 연동, 관제 인시던트 기록, HIGH 등급 사건에 대한 Slack 알림 흐름을 구성했습니다.

04 · ACTUAL TEST SCREENS

직접 실행하고 확인한 화면

10월 30일 실제 테스트에서 캡처한 종합 관제와 로그 파이프라인 화면입니다. 수집·화면 갱신·상태 분류가 연결되는지 확인했습니다.

05 · MY ROLE

내가 주도적으로 구현한 부분

GIGANG은 팀 프로젝트이며, 관제 UI 작업을 제외한 주요 수집·분석·연동·대응 기능 구현을 주도했습니다. 기능의 개발 범위와 테스트 결과를 중심으로 제 역할을 정리했습니다.

이벤트 수집·전달

브라우저·단말·DB 관련 이벤트를 모으고 서버로 전달하는 흐름, 수신·정규화·검증 과정 구현

분석 엔진 및 점수 체계

민감정보 검사 결과와 자료 연관성을 기반으로 동적 점수를 계산하고 사건 상태·근거를 관리하는 로직 구현

서버 및 단말 연동

정책 API와 차단·일시 허용 등 대응 흐름을 연결하고 실제 동작 시 전달되는 데이터 확인

통합 테스트·문제 해결

수집부터 관제 반영까지 연동 테스트를 실행하고, 누락된 필드·중복 처리·점수 불일치 등 문제를 점검·수정

06 · TEST & RESULT

테스트 결과로 확인한 동작

실제 연동 테스트를 진행했고, 아래 값은 테스트 화면을 캡처한 시점의 수치입니다. 운영 환경 성능이나 정확도 지표를 뜻하지 않습니다.
