02 / PROBLEM SOLVING

이렇게 해결했습니다.

기능을 나열하는 대신, 처음의 생각과 수정한 이유, 그 결과를 순서대로 기록했습니다.

CASE 01 PROBLEM → CHANGE → RESULT

오류 개수 세기에서 로그인 패턴 탐지로 확장하다

어떤 점이 문제였나

초기 탐지는 HTTP 400 이상 응답과 IP별 오류 횟수 중심이었습니다. 이런 방식으로는 여러 계정을 대상으로 한 로그인 실패 패턴을 구분하기 어려웠습니다.

이렇게 바꿨습니다

같은 IP의 60초 내 로그인 실패 5회 이상을 Brute Force로, 300초 안에 서로 다른 계정 3개 이상의 실패를 Password Spraying으로 분리했습니다. 심야 로그인과 일반 HTTP 오류도 별도 규칙으로 처리했습니다.

결과와 의미

오류 총량만 보는 대신 시간과 대상 계정이라는 맥락을 반영한 경보를 만들었습니다.

CASE 02 PROBLEM → CHANGE → RESULT

중복 경보와 시간 형식 때문에 생기는 혼란을 줄이다

어떤 점이 문제였나

계속 추가되는 로그를 감시할 때 같은 사건이 반복 알림으로 쌓일 수 있고, 시각이 분 단위인지 초 단위인지에 따라 시간창 판단도 달라질 수 있었습니다.

이렇게 바꿨습니다

중복 경보 제거와 라이브 감시의 알림 쿨다운을 도입했습니다. 로그인 시각의 HH:MM·HH:MM:SS 형식을 처리하고 시간창 경계 테스트를 추가했습니다.

결과와 의미

반복되는 탐지와 시간 경계에서 생길 수 있는 오판을 줄이는 방향으로 구조를 개선했습니다.

CASE 03 PROBLEM → CHANGE → RESULT

AI가 실패해도 멈추지 않고, 높은 위험은 사람이 승인하도록

어떤 점이 문제였나

LLM API 키나 네트워크에 의존하면 판단 단계 전체가 멈출 수 있습니다. 또한 고위험이라고 바로 차단하면 오탐의 피해가 생길 수 있습니다.

이렇게 바꿨습니다

AI 호출 실패 시 규칙 기반 판단으로 전환하고, HIGH 경보에 사용자 승인을 넣었습니다. 대응은 계정 잠금·IP 차단 시뮬레이션으로 한정하고, Flask 사건 저장·Slack 알림·Markdown 보고서로 결과를 남겼습니다.

결과와 의미

자동화의 편의성과 사람의 확인 단계를 함께 둔 관제 파이프라인을 만들었습니다.
