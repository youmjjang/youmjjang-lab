쉬엄쉬엄.

‘가까운 곳’이 아니라 ‘정말 쉬러 갈 수 있는 곳’을 찾고 싶었습니다.

낯선 동네에서 잠시 앉아 쉬고 싶을 때는 카페가 아니라 가까운 벤치나 공원이 필요할 수 있습니다. 그런데 일반 장소 검색만으로는 휴식공간을 찾고 실제 걸어갈 경로까지 확인하기 번거로웠습니다. 그래서 현재 위치와 검색한 장소를 기준으로 휴식 후보를 탐색하고 보행 경로를 안내하는 웹 서비스를 만들었습니다.

01 / WHY THIS PROJECT

먼저, 무엇이 불편하거나
잘못됐는지 생각했습니다.

지도에는 공원·벤치·쉼터 데이터가 서로 다른 형태로 들어 있고, 어떤 장소는 정확한 앉을 자리나 입구 위치가 표시되지 않습니다. 찾기와 길안내를 각각 다른 서비스에서 해야 한다면 사용자가 다시 검색해야 합니다.

02 / PROBLEM SOLVING

만들면서 마주친 문제를
이렇게 해결했습니다.

기능을 나열하는 대신, 처음의 생각과 수정한 이유, 그 결과를 순서대로 기록했습니다.

CASE 01 PROBLEM → CHANGE → RESULT

흩어진 지도 데이터를 한 번에 비교할 수 있게

어떤 점이 문제였나

벤치, 정자, 공원은 지도 태그와 데이터 출처가 서로 달라 한 종류의 검색만으로는 후보가 충분하지 않을 수 있었습니다.

이렇게 바꿨습니다

OpenStreetMap·Overpass에서 착석시설과 공원 후보를 나눠 조회하고, TMAP 공원 검색을 결합했습니다. 거리순 목록과 지도 마커를 함께 보여주고 결과가 부족하면 반경을 넓히도록 만들었습니다.

결과와 의미

장소 유형이 다르더라도 하나의 목록에서 근처 휴식 후보를 비교하도록 흐름을 단순화했습니다.

CASE 02 PROBLEM → CHANGE → RESULT

가까워 보인다고 실제 보행 시간이 짧은 것은 아니어서

어떤 점이 문제였나

직선거리가 짧은 장소도 건물이나 도로 때문에 돌아가야 할 수 있습니다. 모든 장소를 무조건 최단거리로 안내하는 것은 부정확하다고 봤습니다.

이렇게 바꿨습니다

가까운 후보부터 TMAP 보행 경로를 요청하고, 선택한 장소에는 별도 경로를 계산하도록 구성했습니다. 경로 요청이 실패할 때 직선거리를 보행 경로처럼 보여주지 않고 실패 상태를 안내합니다.

결과와 의미

실제 경로가 확인된 경우와 그렇지 않은 경우를 구별해 사용자의 판단을 돕도록 했습니다.

CASE 03 PROBLEM → CHANGE → RESULT

외부 API가 실패해도 화면이 이유 없이 비지 않도록

어떤 점이 문제였나

Overpass 서버 연결 문제, 브라우저 CORS 제한, API 키나 위치 권한 누락으로 검색·안내 기능이 실패할 수 있었습니다.

이렇게 바꿨습니다

Overpass 요청을 서버에서 중계하고 허용된 서버를 순차 시도하도록 했습니다. 요청 캐시와 중복 조회 합치기를 적용하고, GPS 권한이나 경로 API가 없을 때에는 가능한 기능과 실패 사유를 구분해 표시하도록 정리했습니다.

결과와 의미

외부 서비스의 불안정성을 완전히 없애지는 못하지만, 무엇이 안 되는지 알 수 있게 설계했습니다.
