웹 로그에 4xx나 5xx 응답이 많다고 해서 모두 같은 문제라고 볼 수는 없습니다. 저는 초기에 오류를 하나의 기준으로 묶어 분석했지만, 그 방식으로는 어떤 Host/IP를 먼저 확인해야 할지 충분히 설명할 수 없다는 점을 발견했습니다. 그래서 오류 유형별로 판단 기준을 다시 실험하고, 그 결과를 실제 로그 분석 도구에 연결했습니다.

02 / PROBLEM SOLVING

만들면서 마주친 문제를
이렇게 해결했습니다.

기능을 나열하는 대신, 처음의 생각과 수정한 이유, 그 결과를 순서대로 기록했습니다.

CASE 01 PROBLEM → CHANGE → RESULT

4xx를 한 그룹으로 묶었던 첫 실험을 바꾸다

어떤 점이 문제였나

처음에는 4xx 전체에 하나의 반복 횟수와 시간 기준을 적용했습니다. 하지만 401/403, 404, 429는 의미와 발생 패턴이 다릅니다.

이렇게 바꿨습니다

401/403·404·429·5xx 네 범주로 나눈 뒤 30·60·120초의 시간창과 3·5·8·12회의 기준을 조합해 총 48개 조건을 비교했습니다.

결과와 의미

모의실험에서 유형마다 F1이 가장 높은 조건이 다르게 나타났습니다. 최종 기준을 프로그램의 기본 분석 규칙으로 연결했습니다.

CASE 02 PROBLEM → CHANGE → RESULT

‘몇 번 발생했나’보다 ‘왜 확인해야 하나’를 먼저 보여주다

어떤 점이 문제였나

초기 화면은 Host/IP와 숫자, 임계값이 먼저 보여 사용자가 탐지 이유를 바로 이해하기 어려웠습니다.

이렇게 바꿨습니다

어느 경로에서 무슨 오류가 몇 초 안에 몇 번 반복됐는지 문장으로 설명하고, 판단 근거가 된 로그와 주요 경로를 함께 보여주는 형태로 결과 화면을 수정했습니다.

결과와 의미

로그를 처음부터 모두 읽지 않아도 우선 확인 대상을 좁히고 근거를 따라갈 수 있는 흐름을 만들었습니다.

CASE 03 PROBLEM → CHANGE → RESULT

입력 데이터가 매번 깔끔하지 않다는 점을 고려하다

어떤 점이 문제였나

실제 분석 대상은 형식이 섞이거나 일부 행이 손상될 수 있습니다. 올바른 예제 한 개로만 확인해서는 도구를 신뢰하기 어렵다고 봤습니다.

이렇게 바꿨습니다

Nginx/Apache 로그와 CSV·JSON/JSONL 입력을 처리하도록 구성하고, 잘못된 줄이 섞인 예제와 대량 로그 예제로 결과를 점검했습니다.

결과와 의미

유효한 행의 분석과 잘못된 입력 보고를 구분해, 문제를 발견하기 쉬운 처리 흐름을 만들었습니다.

03 / RESULTS & LEARNINGS

검증하고, 남긴 결과

숫자를 그대로 결과로 쓰지 않았습니다

401/403은 60초·5회(F1 0.950), 404는 120초·8회(0.950), 429는 60초·3회(0.961), 5xx는 30초·3회(0.934)가 모의실험 비교에서 높게 나타났습니다. 이는 특정 실험 데이터 기준의 결과로, 실제 운영 환경의 탐지 정확도라고 주장하지 않습니다.
